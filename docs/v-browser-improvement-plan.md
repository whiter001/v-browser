# v-browser 通用功能优化提升方案

下面这份清单聚焦 v-browser 的通用能力，不绑定具体站点。目标是把它做成更稳定、更可预测、更适合自动化 Agent 使用的浏览器控制面。

## P0

| 项目             | 问题                                                                 | 建议改进                                                              | 验收标准                                       |
| ---------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------- |
| 连接恢复与自诊断 | 连接失败时，用户很难快速判断是扩展、浏览器、端口还是当前标签页的问题 | 在 `connect`、`status`、`open` 等关键命令里增加分层诊断和明确修复建议 | 出错时能直接告诉用户下一步该做什么             |
| 结果校验闭环     | 现在很多动作“看起来点了”，但没有统一确认是否真正生效                 | 为 `click`、`fill`、`upload`、`eval` 这类操作补充统一的后置验证模式   | 操作后能自动确认状态变化，而不是只返回执行成功 |
| 动态页面稳定性   | SPA 页面中，DOM 更新、异步渲染和重绘很容易让操作失效                 | 增加更强的等待、重试和可见性判断策略                                  | 对动态页面的成功率显著提升                     |

## P1

| 项目             | 问题                                                           | 建议改进                                                                      | 验收标准                               |
| ---------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------- |
| 语义定位增强     | 仅靠 CSS selector 很容易脆弱，遇到重复按钮或嵌套组件时容易误点 | 强化 `find role/text/label/placeholder/testid` 的组合定位能力，支持上下文限定 | 相同文本的多个按钮可以稳定区分         |
| 富文本与表单输入 | 直接改 DOM 值在 React / 富文本场景中不稳定                     | 对 `fill`、`type`、`keyboard type` 做输入模型说明和回退策略                   | 输入后页面状态与实际输入保持一致       |
| 上传与附件链路   | 文件上传之后通常还要等待预览、绑定和状态同步                   | 提供上传完成、预览出现、附件绑定完成的分阶段反馈                              | 能确认文件已经真正进入页面状态         |
| 复制粘贴与剪贴板 | 需要用户自己拼接复制粘贴流程，链路冗长                         | 把剪贴板相关操作纳入一等支持，减少手工组合步骤                                | 常见复制粘贴流程可一步完成或少步骤完成 |

## P2

| 项目           | 问题                                 | 建议改进                                                                   | 验收标准                                         |
| -------------- | ------------------------------------ | -------------------------------------------------------------------------- | ------------------------------------------------ |
| 调试可观测性   | 页面出错时只看文本不够，定位慢       | 增强截图、注释截图、网络请求、控制台和错误输出的关联                       | 排查问题时能快速看到“页面、网络、控制台”三层信息 |
| 长脚本执行体验 | 长 JS 容易被 shell 引号或换行卡住    | 更强地推广 `--stdin` / `--file` / `--base64` 执行方式                      | 长脚本执行更稳定，不容易卡终端                   |
| 回归测试覆盖   | 核心链路容易在改动后退化             | 增加连接、导航、输入、上传、对话框、iframe、storage、网络拦截的 smoke 测试 | 每次改动能覆盖关键交互链路                       |
| 文档入口清晰度 | 入口多，但不同文档之间的关系不够直观 | 统一把 SOP、命令参考、技能说明、改进清单串起来                             | 新用户能按文档快速上手并找到下一步               |

## 推荐迭代顺序

1. 先做连接恢复与自诊断。
2. 再做结果校验闭环。
3. 接着强化语义定位和输入稳定性。
4. 然后补上传、调试可观测性和回归测试。
5. 最后统一文档入口和使用路径。

## 可落地方案拆解

### 1. 连接恢复与自诊断

- 代码落点：`packages/server/src/main.v` 负责 `connect` / `status` 的入口，`packages/server/src/output.v` 负责错误码分类，`packages/server/src/server.v` 或 IPC 状态返回负责健康字段。
- 在 `connect` 失败时，按错误类型分流输出诊断信息：扩展未加载、扩展 ID 不匹配、relay 端口未通、当前标签页是错误扩展页、浏览器进程未启动。
- 给每种错误补一条明确修复建议，而不是只返回通用失败；例如把“没有扩展连接”拆成“先加载扩展”与“扩展已加载但未 attach”两类。
- 为 `status` 增加更完整的健康检查字段，例如 `browserConnected`、`extensionAttached`、`relayReachable`、`activeTabType`，并在非 JSON 输出里保留一句可操作的提示。
- 验证方式：在 `packages/server/tests/test-connect.ps1` 和 `packages/test-ui/smoke-cli.sh` 增加断连、错误扩展页、端口不可达三类 smoke，用来确认输出里包含下一步动作。
- 验收方式：用户只看一次错误信息，就能知道是要重连、重启浏览器、重新加载扩展，还是切回普通标签页。

### 2. 结果校验闭环

- 代码落点：`packages/server/src/commands.v` 负责各类动作命令，`packages/server/src/main.v` 负责 CLI 参数和输出包装，`packages/server/src/output.v` 负责统一结果格式。
- 给关键命令加“执行后检查”模式，例如 `click --verify`、`fill --verify`、`upload --verify`、`eval --verify`。
- 结果校验优先使用同一套规则：可见性变化、URL 变化、文本变化、属性变化、按钮 disabled 状态变化、附件是否出现、下载是否完成。
- 对可能是异步完成的操作加一个超时等待窗口，并提供 `--verify-timeout` 或等价参数，避免固定 sleep。
- 对高风险操作保留一个显式开关，让用户选择是否严格等待后置校验，避免把所有场景都绑死在强校验上。
- 在输出层把“执行成功”和“结果确认成功”区分开，必要时返回 `state` 或 `verified` 字段，而不是只有一条字符串。
- 验证方式：在 `packages/test-ui/lab.html` 里补固定靶点，分别覆盖按钮状态变化、文本变化、URL 变化、附件预览变化和下载完成五类结果。
- 验收方式：每个命令都能清楚回答“动作发出去了没有”和“页面状态真的变了吗”这两个问题。

### 3. 语义定位增强

- 代码落点：`packages/server/src/commands.v` 里的 `find`、`click`、`hover`、`fill` 相关选择器解析，`packages/server/src/server.v` 的快照/调试输出，`packages/test-ui/lab.html` 的定位靶点页面。
- 扩展 `find` 的组合过滤：`role + name`、`text + container`、`testid + nth`、`label + visible`、`placeholder + visible`，并允许把多个条件串成一个查询。
- 为重复按钮和列表项增加上下文限定，例如先锁容器，再找内部按钮；必要时支持“先选父节点，再在子树内搜索”的两步定位。
- 在 `snapshot`、`get box` 或调试输出里标出更清晰的可见性、层级、文本片段和可点击状态，减少只看 CSS selector 的风险。
- 对定位失败输出更有帮助的错误，例如“同名元素有 3 个，建议加 `name` 或 `container` 限定”，而不是只给 element not found。
- 验证方式：在测试页面中放置多个同名按钮、重复链接、嵌套表单和隐藏元素，确认定位结果稳定可复现。
- 验收方式：用户不需要猜 selector，就能通过语义条件稳定点到目标元素。

### 4. 富文本与表单输入稳定性

- 代码落点：`packages/server/src/commands.v` 里的 `fill`、`type`、`keyboard` 相关实现，`packages/test-ui/lab.html` 的输入靶点页面，必要时补 `packages/server/src/output.v` 的错误提示。
- 统一输入策略：`fill` 走清空后输入，`type` 走真实按键事件，`keyboard type` 走当前焦点输入，三者的语义和适用场景写清楚。
- 对 React / contenteditable / 富文本场景，必要时同时触发 `input`、`change`、`blur` 等事件，并在受控输入下检查最终值是否真正反映到页面状态。
- 对直接写 DOM 值的路径做明确边界说明：仅用于简单输入框，不作为富文本或受控组件的通用方案。
- 对输入命令提供更明确的反馈，例如“已输入但未确认提交”与“页面已收到并持久化”区分开。
- 验证方式：在测试页里覆盖 textarea、contenteditable、React 受控输入、自动格式化输入四种模型，分别检查值、光标和事件触发。
- 验收方式：用户对文本输入、富文本输入、快捷键输入的结果都能得到稳定且一致的页面状态。

### 5. 上传与附件链路

- 代码落点：`packages/server/src/commands.v` 的 `upload` 实现，`packages/server/src/commands.v` 或 `server.v` 中的下载/附件状态返回，`packages/test-ui/lab.html` 的上传桩和预览桩。
- `upload` 后返回上传结果、文件名、可见预览状态、附件数量和是否已完成绑定，不只返回“已点击上传”。
- 对需要后续编辑描述或继续操作的场景，提供一个可选的 `upload --wait-preview` 或类似等待模式，等到预览卡片真的出现再返回。
- 对 blob 预览、附件卡片、元数据绑定状态做标准化输出，便于脚本后续判断附件是“已选中”“已上传”“已展示”还是“已绑定”。
- 对上传失败补充可操作的错误提示，例如权限不足、文件不存在、浏览器拦截、站点不接受该文件类型。
- 验证方式：在 test-ui 里固定一个上传桩，检查上传后是否生成预览、是否能继续编辑附件属性、是否能区分成功上传和仅选择文件。
- 验收方式：脚本上传完文件后，不需要人工看页面，就能判断附件到底处于哪一步。

### 6. 调试可观测性

- 代码落点：`packages/server/src/output.v` 负责错误码和 JSON 包装，`packages/server/src/main.v` 负责 CLI 层的友好提示，`packages/server/src/commands.v` 负责各命令的调试信息补充，`packages/test-ui/lab.html` 负责制造可复现失败样本。
- 增强 `--json` 输出，让结果结构化包含 `ok`、`error`、`suggestion`、`state`、`hint`，并在必要时区分命令执行失败和页面验证失败。
- 在出错时统一建议用户补充 `screenshot`、`console`、`errors` 和 `network requests` 的信息，并把这些命令写进错误提示里。
- 为动态页面提供一个“调试三件套”路径：页面文本、截图、请求日志；如果还不够，再加页面快照或 DOM 片段。
- 对高频错误统一做分类映射，例如未连接、元素未找到、超时、权限问题、下载失败、上传失败，让错误信息更可读。
- 验证方式：对典型失败案例补充标准化错误输出，避免只剩一行 `Error`，并检查 JSON 与非 JSON 两种模式下的信息一致性。
- 验收方式：用户拿到错误后，不需要回头猜命令，就能直接按提示继续排查。

### 7. 回归测试覆盖

- 代码落点：`packages/test-ui/lab.html` 作为核心 fixture，`packages/test-ui/smoke-cli.sh` 作为 CLI smoke，`packages/server/tests/test-connect.ps1` 和其他现有脚本作为平台相关回归入口。
- 把 `packages/test-ui/lab.html` 作为核心 fixture，补全连接、输入、上传、对话框、iframe、storage、网络拦截、下载和失败提示等关键场景。
- CLI 层增加 smoke 脚本，覆盖 `connect`、`open`、`snapshot`、`eval`、`upload`、`dialog`、`find`、`wait`、`tab` 这几个高频链路。
- 对关键命令补最小回归测试，例如：连接恢复、错误码分类、输入事件触发、附件上传、选择器定位和 JSON 输出。
- 给 smoke 测试统一一份“通过标准”，例如返回码、输出文本、状态字段、页面文本、附件是否存在，避免只看是否跑完。
- 验证方式：在 CI 里跑最小 smoke 流程，确保核心链路在每次改动后都能过，并在失败时能直接定位到是哪一类能力退化。
- 验收方式：每次核心命令变更后，都有一条能自动证明没有回退的路径。
